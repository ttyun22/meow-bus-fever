# 🐱🚌 猫咪巴士大疏通

一款「猫咪上车 + 停车场疏通」的轻量休闲 H5 游戏。停车场里塞满彩色巴士，
猫咪们按颜色在站台排队。点击巴士让它沿**车顶白色箭头**方向驶出，进入
**4 个基础接客位**（每关可用 2 次「加位」救援，最多额外 +2 个临时位）；每辆车有
**独立载客容量 2/4/6**（2 座=2 格短车、4 座=3 格中车、6 座=4 格长车），
同色猫咪依次上车，达到自身容量后立即离场并腾出车位（接完同色猫时也会发车）。
满位时新车辆进入**等待队列**，不占用接客位。HUD 的「提示」会根据当前队首、
车位、车辆容量和真实可执行操作生成下一步建议；BGM 与音效可分别开关。

纯前端实现（HTML + CSS + JavaScript ES Modules），**无后端、无运行时外部依赖**。
开发时本地静态服务即可运行；部署时 `npm run build` 会把运行时文件整理到 `dist/`，
供 Vercel 等静态托管直接发布。

## 二、本次修复的根本原因

旧版生成器虽然也按阻挡拓扑序给车辆上色，但队列组顺序固定采用
「下一组 → 上一组」的成对交换，导致：

1. **开局队首经常不是开局可动车辆的颜色**：车辆布局、阻挡顺序和队列组
   分别按自己的规则拼在一起，没有检查「开局队首是否有合法车」。
2. **所有生成关卡的队首几乎都是蓝色**：色盘始终从同一个偏移开始，
   只换车辆数量，不能形成真正的颜色/路线变化。
3. **槽位压力被固定成同一套路**：总是停 3 辆、留 1 个空位，轻微点错
   就会占满 4 个接客位，缺少缓冲，也没有救援。
4. **布局模板单一**：基本只有「竖直通道先清、横向车道后清」一种结构，
   难度主要靠加车。
5. **验证只证明参考解能通关，没有检查开局正反馈、队首匹配、单点阻挡
   扇出、布局重复等质量指标，也没有对玩家失误的恢复机制。**

本次把「布局 → 阻挡拓扑序 → 颜色/容量 → 队列组顺序 → 状态回放 →
质量约束」合并成同一条生成链，并新增免费救援。

### 接客位堵死问题的修复（本轮）

确认的根因不是「4 个接客位数量不够」，而是状态与调度不完整：

1. 车辆只有 `board/loading/departed`，没有区分 `waiting/moving/loading/
   departing/completed`，动画与逻辑共用同一个「已发车」状态；
2. 满位时 `validateMove` 直接拒绝，`anyLegalMove` 也直接返回 false，
   四格占满会把所有合法点击一起锁死；
3. 没有等待队列，点击既不能排队也不能推进；
4. 同色多车按 `slots` 数组顺序取车，而不是按实际进入接客位的先后顺序；
5. 失败判定把「接客位满」间接当成「无操作」；
6. 车身长度与容量各自独立配置，存在 2 座长车/6 座短车的状态不一致。

修复后：

- 车辆状态：`waiting → moving → loading → departing → completed`，
  `slotIndex` 只允许存在于 `moving/loading`；
- 接客位与车辆双向原子绑定；满员时 `departing` 立即释放车位，
  动画结束只把旧车标为 `completed`，**不会再次释放已被新车占用的车位**；
- 四格占满时点击合法车辆进入 `waiting` 队列，不占接客位；
  任一车位释放后按等待顺序派车，被车阵挡住的队首不会锁死整条队列；
- 同色车辆按 `arrivalOrder` 先来后到；最早同色车还在 `moving` 时，
  后到同色车不能抢客；
- 失败判定只在「无 moving/departing、队首无法上车、无车可发车、
  无空位可推进」时成立，不再以「四格全满」判负。

## 三、协同生成流程

### 1. 车辆先完整建立
每辆车包含：颜色、位置、朝向、**独立载客容量（2/4/6）**和由容量唯一映射的车身长度
（2 座=2 格、4 座=3 格、6 座=4 格），以及由车头路径推导出的驶出条件。
容量与长度必须严格对应，配置校验会拒绝任何 2 座长车或 6 座短车。

### 2. 从阻挡关系计算移除拓扑序
布局由「错落纵向车列 + 错落横向车道」建立：每条纵向列只占随机的一段行、
每条横向车道只占部分列，车辆之间随机留 1 格空隙，再通过转置/镜像得到不同模板：
- 纵向车列先清、横向车道后清；
- 或转置成横向车道先清、纵向车列后清。

生成器会拒绝「整行/整列被占满」以及「连续 12–14 格车墙」的布局，
保证横向/纵向混合、前后错位、局部聚集与留白。

拓扑序中的每一辆车，在它被移除时车头路径一定已经清空。

### 3. 队列由拓扑序、颜色、容量共同生成
- 按拓扑序切组：前期每 2 辆一组，后期每 3 辆一组；
- 同组车辆同色，队列对应连续色块，长度 = 这些车的**各自容量之和**；
- 每辆车容量由车身长度映射（2/3/4 格 → 2/4/6 座），并强制同一关至少混用三种容量；
- **第一组永远按拓扑序先服务**：开局队首颜色一定与拓扑序第一辆同色，
  因此开局必有「队首同色且可驶出」的车，先点就能得到正反馈；
- 后续按难度概率交换相邻组：玩家先把前一组（2–3 辆）停进接客位，
  留 1–2 个空位，再接下一组同色猫；
- 色盘每关重新洗牌，队首颜色不再固定为蓝色。

### 4. 质量约束（不通过就换布局/换队列重新生成）
- 所有关卡统一 4 个基础接客位（救援时可临时增加到 5/6 个）；
- 每辆车容量必须是 2/4/6；第 10 关起每关必须混用三种容量；
- 队列长度 = 车辆总容量；每只猫都有对应的同色容量；
- 不允许整行/整列被车辆占满，最长连续车墙不超过场地边长的 72%；
- 开局可动车辆 ≥ 4（按车辆数计算比例），且不超过 45%；
- 开局至少 1 辆「队首同色且可驶出」的车；
- 单辆车最多直接阻挡 10 辆，单车最多被 8 辆挡住；
- 依赖链至少 3 层，高密度关卡通常 5–8 层；
- 50 关布局签名互不重复；
- 每关参考解使用游戏同一套 `logic.js` 逐步回放，必须真实到达 `won`；
- 每一步检查接客位/车辆状态一致性。

### 5. 难度变化
难度来自：布局错落程度、横/纵方向、依赖链深度、单点阻挡扇出、组交换次数、
每组成员数（2 或 3）、车辆密度、颜色数量与容量组合，而不只是车辆数量。

| 关卡区间 | 车辆数 | 接客位 | 场地 | 主要变化 |
| --- | ---: | ---: | --- | --- |
| 1–5 | 2–6 | 4 | 5×3–7×6 | 核心循环、阻挡、颜色顺序、2/4/6 容量 |
| 6–9 | 5–6 | 4 | 5×5–6×5 | 多方向、长短车、纵向阻挡 |
| 10–19 | 31–38 | 4 | 12×12 | 协同起步，每 2 辆一组，多数关卡顺队列 |
| 20–34 | 38–48 | 4 | 13×13 | 组交换入门，2/3 辆组混合 |
| 35–50 | 49–60 | 4 | 14×14–15×15 | 高密度组交换，每 3 辆一组为主 |

第 10 关 31 辆；第 20 关 38 辆；第 30 关 46 辆；第 40 关 53 辆；
第 50 关 60 辆。第 10 关之后全部 >30 辆。

## 四、救援：增加临时停车位

每关提供 **2 次**加位救援（`GAME_CONFIG.RESCUE_LIMIT`），每次临时 +1 个接客位，
整关最多额外增加 **2 个**（`GAME_CONFIG.EXTRA_SLOT_LIMIT`）：

- 点击 HUD 的「加位 2」后先弹出确认框，明确显示当前已加几个、剩余次数和实际效果；
- 确认后由 `addTemporarySlot` 原子追加一个 `{ extra: true }` 接客位，立即参与
  等待队列派车、接客与离站，不改变车辆颜色、容量或载客规则；
- 新增位置有独立「临时」徽标和橙色描边，不会与原有车位、车辆或道路重叠；
- 只有成功执行才扣 1 次；次数为 0、已 +2、已通关或状态不稳定时不会改动任何数据；
- `rescueLock` + 短窗口锁防止同一次救援被连点重复触发/扣费；
- 新关卡与「重开本关」都会把次数恢复为 2；
- 旧的颜色队列调整函数仍保留在 `logic.js` 中作为调试/历史能力，但已不作为 UI 入口，
  也不会被宣称为「必然解死局」；真正的可解性由关卡生成与搜索验证保证。

失败覆盖层会优先提示加位是否真的能帮助当前局面；如果停车场里没有可驶出的巴士，
会明确说明「加位也无法被使用」，而不是机械推荐救援。

## 五、接客位、容量与连续操作

- 所有关卡统一 4 个**基础**接客位；救援可临时增加到 5 或 6 个。接客位数量与巴士容量是两个独立配置。
- 每辆车独立记录 `capacity`（2/4/6）与 `passengers`，车身长度由容量唯一映射；
  接客位顶部固定显示 `🐾 当前/容量`，例如 `1/2`、`3/4`、`5/6`，标签位于车身上方。
- 车辆状态：`board/waiting/moving/loading/departing/completed`。
  `moving` 表示已原子预留车位、动画未到位，不能上车；`loading` 才允许上车。
- 任意一辆车达到自身容量就**立即**变为 `departing` 并原子释放对应车位；其他车继续
  接客，互不等待。动画结束只把旧车标为 `completed`，不会重复释放车位。
- 接客位满载时，点击合法车辆会进入 `waiting` 队列，不占接客位、不锁死其他点击；
  已有车辆继续接客并离开，空出的车位按等待顺序接纳下一辆车。
- 同色多车严格按 `arrivalOrder`（实际进入接客位的先后）上客；最早同色车还在
  `moving` 时，后到同色车不能抢客；它离开/完成后下一辆才成为优先车。
- 玩家可以在上一辆车播放动画时继续点击其他合法车辆。
- 独立 `exitQueue` 为动画排队：连续点击时动画按提交顺序衔接，同一时刻
  最多一辆车处于驶出动画，避免重叠/穿模。
- `inTransit` 只影响显示（「驶入中」），不再承担状态语义；状态由 `moving/loading` 决定。
- 猫咪上车动画整体提速 1.5 倍（原 360ms 行驶段 → 240ms），不跳帧、不跳过动画；
  逻辑上车在动画完成前原子提交，因此不会重复上车。
- 被阻挡车辆抖动、挡路车闪烁、toast 指出阻挡颜色，不扣资源、不判负。

## 六、失败判定

失败只在以下条件同时成立时触发：

1. 没有 `moving/departing` 等未落定转换（`loading` 是稳定可结算状态）；
2. 接客位里没有巴士能接走当前队首（遵守同色先到先得）；
3. 接客位里没有巴士能满足发车条件（满载或该色已接完）；
4. 没有任何「空位 + 可驶出车辆」的推进路径。

因此「接客位暂时占满」本身不会判负；等待队列也不会被当作可推进路径。
只有确实无法继续时才失败。失败后优先判断「加位」是否能提供可用的新位置，
否则直接提供重开；撤回入口已从正式 UI 移除。

## 七、智能提示、视觉与 BGM

- HUD 下方常驻一条智能提示，每次车辆移动、猫咪上车、满员离站、加位后重新读取
  `state` 并更新；同一状态相同文案不会重复刷新。
- 提示会区分：接客位全满、同色多车先来后到、队首连续猫数与车辆剩余容量不匹配、
  队首同色车被挡时应先移哪辆、加位是否真的能帮上忙；并返回具体车辆 id。
- 若搜索器能证明某次点击会失去所有通关路径，点击前会弹确认框（「仍然移动」仍可执行）；
  预算不足时只使用「可能 / 无法确定」，不会错误禁止合法操作。
- 猫头保持圆润、统一的贴纸风格：耳朵、内耳、眼睛、鼻子、笑嘴、胡须、腮红。
- 不使用完整人形/四足身体、四肢、尾巴、骨骼动画或外部 3D 资源。
- 轻量动画：队列浮动、眨眼、FLIP 补位、上车漂浮 + 弹跳缩小、接客位弹跳。
- 基础 4 个接客位在 390px 宽容器下同排显示；6 个车位（含 2 个临时位）在 320px
  下仍不重叠，HUD 按钮会自动收窄；手机竖屏 HUD 自动分两行，技能按钮 ≥40px。
- BGM 使用本地合成资源：`assets/bgm-cat-bus.m4a`（64 kbps AAC，约 260 KB，优先加载）
  与 `assets/bgm-cat-bus.wav`（无损兜底）。114 BPM、16 小节、C 大调五声音阶，
  木琴 + 玩具拨弦 + 轻打击；`decodeAudioData` + `loop=true` 采样级循环。默认音量
  0.32，低于 SFX，并在每次操作音播放时短暂 duck。浏览器无法解码 WAV 时回退到
  程序化合成；两条路径都有单实例保护，切换关卡不会叠加。首页与 HUD 的音乐开关
  共用同一持久化状态。

## 八、实际验证结果

### 1. 规则层验收（`npm test`，实际运行）

**242 项全部通过**，包括：

- 连续提交 4 辆合法车：立即 `moving`、到位后 `loading`、4 个接客位无重复占用；
- 满位时第 5 辆进入 `waiting`，不占接客位；车位释放后自动进场；
- 接客位全满后已有巴士继续接客、发车、释放；
- 2/4/6 独立容量：2 座接满 2 只立即离场，4/6 座继续接客；
- 同色两辆红车严格按进入接客位的 `arrivalOrder` 先来后到；
- 先到同色车仍在 `moving` 时，后到同色车不能抢客；
- 猫头上车顺序严格 FIFO，载客数准确，每辆车只离场一次；
- 被阻挡车辆不增加操作数、不判负；
- 构造满位且队首不匹配的真实死局：加 1 个临时位后蓝车进场、释放临时位并继续通关；
- 连续两次加位得到 6 个接客位，第三次被拒绝；即使传入更大剩余次数也不能突破 +2 上限；
- 新增临时位后，原本等待的第 5 辆车会立即被派入该位置；
- 临时位参与接客、离站、车位释放；重开/换关恢复 2 次；
- 状态自检能发现临时位标记错误、超过 +2 上限、`slotCount` 不一致；
- 智能提示覆盖：满位需加位、同色多车先来后到、容量与队首连续猫数不匹配、
  队首同色被挡时指向真实挡路车、无加位次数时说明原因；
- 可证明的死局操作被标记为 `proven`，仍可通关的操作不会被误报；
- 50 关参考解全部真实回放通关；
- 50 关全部 4 个基础接客位、第 10 关起 >30 辆、队列长度 = 总容量；
- 全部巴士容量均为 2/4/6 且与车身长度严格对应；第 10 关起混用三种容量；
- 多解法分析覆盖第 1/5/10/30/50 关：每关至少 2 条不同开局完整通关路径，
  样本路径逐条回放通关；第 50 关有界 DFS 60 步通关；
- 50 关布局互不重复；
- 连续重开 20 次、历史快照重放、智能提示读取后状态一致；
- 自检函数能发现重复占用接客位等状态损坏。

## 十、生产构建与 Vercel 部署

项目保持纯前端，不需要后端、数据库或环境变量。生产构建只复制：

- `index.html`
- `src/`（游戏逻辑、渲染、样式、音效）
- `assets/`（BGM、favicon）

`tools/build.mjs` 会校验入口与关键资源齐全，并扫描 `localhost`、`file://`、
`/Users/...` 等部署后失效的引用。`sound-lab.html` 是开发调试页，不进入生产产物。

### 方式 A：Vercel 网页导入（推荐）

1. 把仓库推到 GitHub（须包含本次新增的 `vercel.json`、`tools/build.mjs`）。
2. 登录 <https://vercel.com/new>，选择 **Import Git Repository**。
3. Framework Preset 选 **Other**；构建命令与输出目录会被 `vercel.json` 自动读取：
   - Build Command：`npm run build`
   - Output Directory：`dist`
   - Install Command：默认即可（项目无依赖）
4. 点击 **Deploy**。完成后域名形如 `https://<project>.vercel.app`，
   手机直接打开即可；以后 push 到默认分支会自动重新部署。

### 方式 B：Vercel CLI

```bash
npx vercel login       # 按提示在浏览器授权
npx vercel             # 首次部署，按提示关联项目（预览环境）
npx vercel --prod      # 发布生产环境
```

> 部署不需要任何环境变量。若使用自定义域名，在 Vercel 项目的

## 十一、仍然可能出现死局的条件

1. **玩家仍可能把 4–6 个接客位都停满错误颜色**：如果队首颜色在停车场里
   没有可驶出的同色车，加位也无法让它上车；此时只能重开。这不是状态 bug，
   而是现有严格 FIFO 规则下的真实死局。生成器已通过多解法约束降低概率。
2. **加位不是万能解药**：它只增加空间，不改变颜色、容量、队列顺序或阻挡关系。
   失败覆盖层与提示会明确说明「加位帮不上」的原因，不消耗次数。
3. **高密度关卡没有穷尽全部状态空间**：第 10–50 关使用有界 DFS + 参考解回放
   作为可解性证明；`solutionCount` 是「找到的可行开局下界」（高密度关达到 3
   即停止），不是所有排列的精确总数。搜索预算耗尽会标记 `aborted/未确定`。
4. **关键步只检查前若干步**：高密度关默认只对前 2 步做「唯一获胜选择」检测，
   小关卡检查全部参考步；不会把未搜索的分支冒充成已证明。
5. **等待队列不是无限缓冲**：满位时车辆可以排队，但等待车辆仍停在停车场、
   占用格子；若它们互相阻挡，会按「第一辆可通行车辆」派车，不会凭空穿模。
6. **旧颜色队列调整仅保留为调试函数**：`rescueQueue/useRescue` 仍可被测试或
   调试调用，但正式 UI 只有「加位」；不再宣称换色必然能解死局。
7. **BGM 为本地合成音频**：WAV 由 `tools/generate-bgm.py` 生成，部署时优先加载
   转码后的 `assets/bgm-cat-bus.m4a`，WAV 作为兜底；无外部商业素材。
   首次播放仍依赖浏览器手势解锁，切换标签页时会暂停并在返回时恢复，
   目前没有显式游戏暂停按钮。若 AAC/WAV 都无法解码，会自动回退到
   114 BPM 的程序化合成版本（听感略有差异，但不会静音或叠加）。
8. **高密度关的车辆触控目标偏小**：320px 宽、15×15 棋盘时单格约 17px，已加入
   「点击车旁空隙吸附最近车辆」与 `touch-action: manipulation`，但相比 44px
   标准触控目标仍有差距；这是保证 60 辆车一屏完整可见所做的取舍。
9. **教学只在第 1–5 关**：第 6 关起不再弹新手气泡；玩家仍可随时使用 HUD 的
   「提示」按钮查看基于当前局面的下一步建议。
10. **生成器使用确定性种子**：调参后需重跑
    `npm run generate && npm run verify && npm test && npm run test:seeds`。
